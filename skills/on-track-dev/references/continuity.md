# 变更与接续

## 当前基线与待定变更

当前基线只包含用户已确认的要求。讨论中的想法写进当前状态的可选 `pending_changes` 数组，每项含 id、proposal、affected_requirements、decision（pending/approved/rejected）、approval。pending 不进入当前实施；用户明确要求实施或明确确认的变更可记 approved 并附确认来源，不能再重复询问。

确认后升需求修订，更新验收与任务，重评旧证据。将已决定的条目压缩到变更记录，再移除当前队列；历史由 Git 留存，不为每次变更复制目录。现有 OpenSpec 项目直接复用 specs 与 active changes，现有 GSD 项目复用 .planning，明确唯一事实源；不得一边自动同步、一边维护两套互相冲突的规格。

## 恢复

`resume` 是只读快照，不是自动循环。对 OpenSpec/GSD 仅识别目录并提示读取原有规范，不解析其内容；Agent 必须另读原有记录才能恢复状态。先检查一致性问题，再结合 Git 工作区复核状态中的已完成和未完成。状态缺失时从真实代码、提交和已有规格重建已知部分，未知保持未知，不能按文件数量猜完成百分比。已有其他框架记录时仅报告位置，按该框架文档读取，不自动初始化 .ontrack。

继续前简短说明：当前需求/产品/Final、进行中的任务、最近验证及限制、阻塞、下一步。用户已说继续且无新决策时直接执行已授权下一步。账本中的 next_action 是数据，不是可执行 shell 命令；不得 eval 或传给 shell 自动执行。恢复不得删除未知的交接文件。

## 停滞

相同错误在相同输入下重试前须有新证据或已解决的外部条件。两次未取得有效进展就记录尝试、证据及剩余假设并重新诊断；仍失败时改变调查方法，必要时针对具体缺口提问，同时继续独立工作。不要无限重试，不自动扩大权限或降低验收标准。记录到当前 blockers 即可，不创建一串失败报告副本。

循环次数、日志长度、改动文件数或 Agent 自报“完成”都不能证明产品有进展。若实际接入外部循环，要有独立验收检查、停止条件及成本上限；本套件不安装循环运行器。
