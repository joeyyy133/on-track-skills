# 按当前要求推进开发

默认中文。先理解现有代码、调用链和测试。读取项目 AGENTS.md 和已有管理文件；尊重现有工具与目录，不另建一套重复账本。新项目采用 [项目记录协议](references/protocol.md)，成熟项目可映射到现有文件，并记录映射位置。

## 固定边界

- 当前有效要求是用户最新确认的版本，不是最初对话，也不是 Agent 新写的计划。任务完成授权不能证明新目标获得确认。
- 目标、验收、范围、重要设计变化先说明具体差异、理由、影响和推荐选择，等待用户确认；实现细节自主推进。用户本轮明确提出的变更本身可构成确认，不重复问同一目标；只澄清尚未确定的重要取舍。等待时继续不依赖该决策的工作。
- 需求/实现事实、推断、未知分开；不得编造接口、测试输出、执行记录或历史设计理由。
- 一个当前源码树。Git 保存历史；禁止 V1/V2 源码副本、Final2、每轮备份和默认工作树扩张。不要删除原有文件。
- 产品 V1.0.0 起步；修复升 PATCH、兼容功能升 MINOR、不兼容或重大目标/架构变化升 MAJOR，并在变更记录解释。需求独立编号 REQ-001。开发迭代不必发布。
- Final 是用户已确认版本的指针，与开发 HEAD 分开；只能经本轮明确交付确认后更新，不能把“推进完成”视为对尚未审阅产物的 Final 确认。

## 实施与接续

1. 开始、换会话或压缩后：从磁盘重读需求、状态、决策和版本记录；检查 Git HEAD、工作区和已有改动。对齐需求修订号及内容摘要。摘要过时则重新评估任务和证据；不得只改摘要绕过复核。
2. 把需求拆成可验收条目 R1…，将本轮任务对应到条目，写清验证方式。缺少关键信息时优先查代码，低风险细节自行决定。
3. 实施前简短说明改哪里、主要风险、怎么验证。遇到障碍/替代方案时重新核对约束。小任务保持轻量，不为改文案强建测试体系。
4. 完成一项后记录实际文件、执行命令、结果、限制；区分已写/已运行/通过/未验证。验证须与验收条目相关，编译成功不能代替用户隔离等行为验收。
5. 在完成理解/设计、关键功能实现、验证交付这些重要阶段主动解释：做什么、怎么做、为什么、替代方案、依据及未知。小改动可合并为一次说明。无需等待用户调用另一个 Skill。
6. 结束或中断前原地更新状态：当前任务、真实进度、未验证项、下一步、阻塞、有效需求与版本。用户消息优先核对为需求变更或澄清，不自动替换总目标。

## 可执行核对

新项目先使用 `python3 <此 Skill 目录>/scripts/ontrack.py init <项目绝对路径>`。已有 `.ontrack` 时拒绝覆盖。原生 `.ontrack` 布局按协议填真实记录，再运行 `check`；宣布本轮范围完成前运行 `check --complete`。输出非零时先解决或明确报告未完成，不得降低验收来让检查通过。

使用 `snapshot` 在实际验证前后核对源码摘要并记录证据。普通实现可用 `check --complete` 交付；正式可复现发布再用 `check --release`，不为通过普通验收擅自提交代码。

脚本核对文件与声明的一致性，不能验证用户是否真的确认、日志是否真实或测试是否充分。测试实际通过、代码审查及需求语义核对仍需 Agent 执行。不要把脚本称为已自动强制运行的 Harness；如需 CI/生命周期 hook，另行按项目环境实现并验证。

## 版本、Final 和清理

仅里程碑保留版本交付物，源码不复制。发布时检查干净的 Git 状态、提交、标签与验证证据；不强制用户提交混杂改动，也不自动提交其无关文件。没有 Git/不能提交时可继续实现，但注明发布证据未完成，不宣称可复现正式版本。

原生布局按协议更新发布记录后运行 `check --final`，只在记录匹配真实标签、提交及用户确认时把它称为 Final。先准备可审阅交付物再请求 Final 确认。已有 Final 保持不变直至新版本获确认。

仅清理本任务创建、已登记且可再生成的临时文件，先列候选；拒绝越界、符号链接穿越、通配删除和未追踪用户文件。历史发布/里程碑删除需明确授权。Git 管源码，忽略缓存和可再生构建物，避免仓库也变成垃圾山。

## REA 按需接入

完整源码的普通理解用仓库工具，不触发 REA。只有发布包、二进制或源码未能建立的运行行为需要调查时，参阅 [REA 边界](references/rea.md)。安装此 Skill 不会安装 REA 或任何分析引擎。

采用现有 OpenSpec/GSD 映射布局时，不运行仅支持 `.ontrack` 的检查命令；使用现有框架实际可用的验证及等价的需求、证据、版本和 Final 核对，逐项报告结果。当前脚本未实现这些布局的解析和验收适配，不得为满足脚本另建重复账本。

## 变更、恢复与停滞处理

出现需求变更、会话恢复、重复失败，或已有 OpenSpec/GSD 记录时，读取 [接续与变更](references/continuity.md)。可运行只读命令 `resume <项目绝对路径>` 查看真实当前状态与一致性问题；它不自动执行 next_action，不会修改已有账本。

完成声明按类型选择证明：构建用构建结果、缺陷修复用原症状复验、需求满足用逐条验收；Agent 自报和任务勾选都不能代替证据。最近一次失败/未运行记录不得被早期成功遮蔽。快照摘要也不覆盖外部依赖与被排除产物，发布包需单独检查。
