# 理解项目并审查设计

默认中文，先用户行为，再数据流，再必要的技术细节。主动在重要阶段说明，不要求用户掌握术语。与实施同时使用时沿用执行授权；单独解释请求不扩展为改代码。

## 先建立真实现状

读取项目 AGENTS.md、README、需求/状态/决策/发布记录（通常 `.ontrack/`，已有项目用现有记录）。核对 Git HEAD、工作区与用户指定版本。Final 可能落后于开发版本，要明确区分。没有记录时通过代码建立解释，不擅自初始化一套账本。

围绕用户所问功能，从入口沿真实调用链追到状态与数据存储，抽查相关测试。文档和代码冲突时分别说明，不能选一个顺口的版本。只看过局部就只解释局部，不宣称掌握全部架构。

## 阶段说明的内容

按问题规模取舍，避免每次套大报告：

1. 当前目标、有效需求版本、产品版本、Final 和已验证状态。
2. 用户做什么、系统产生什么结果。
3. 输入 → 模块/接口 → 数据与状态变化 → 输出，用关键文件链接支撑。链路复杂时用短 Mermaid 图；不要画未核实依赖。
4. 为什么这样设计：已知约束、实际决策、考虑过的替代方案及代价。只有推测的历史原因明确写推断；未知写未知。
5. 如何确认正确：真正运行的检查、结果和未覆盖部分。区分代码已写、编译通过、功能验证、正式交付。
6. 接下来做什么、需要用户决定什么。

对“代码如何形成”优先提供需求条目 → 设计选择 → 关键改动 → 验证的映射。有 Git 证据可说明变化历史；没有就不能编造开发过程。

## 帮用户 challenge

主动指出最易错假设、反例和成本。解释一个更简单的替代方案，说明什么条件会推翻当前选择。根据代码回答可查问题，不把代码调查转成用户问卷；对产品取舍提供推荐再提问。

用户可直接这样问：
- 从点击开始到保存结束，沿代码解释一次。
- 哪些是事实，哪些是推断？证据在哪里？
- 去掉这一层会怎样，为什么需要它？
- 哪种失败场景尚未验证？什么证据会让你换方案？
- 当前版本与 Final 差在哪里，怎样回退？

不自动调用不存在的 Skill 工具；若另一个 Skill 可用，显式读取其文件，不能只写“调用某技能”就视为已执行。REA 仅用于源码不足的产物/运行证据调查；普通源码解释不启用逆向工具，不暗示 REA 能恢复原始设计动机。

## 解释后的边界

发现问题时指出位置、影响及验证方法。改变目标、验收、范围或重要设计必须等待用户确认；解释模式中先提出修复建议，不自主实施。更新文档只有在当前任务授权包括记录时才做，并沿用已有文件，禁止每次产生 explanation-v2 等副本。

## 阶段说明中的变更差异

涉及迭代时分别说明当前已确认基线、尚待决定的提案、实际实现、最近验证四者的差别。已有 OpenSpec/GSD 时引用原有文件，不初始化第二套记录。任务勾选、文档声明或另一个 Agent 自报成功只能作为线索，核对差异和行为证据后再做结论。
